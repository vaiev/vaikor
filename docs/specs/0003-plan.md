# 0003 – Plan language v0.2 (VKR-L3)

> **Status:** Draft v0.2. Accepted as the target of Phase 3. `runtime/vaikor-verify` still implements v0.1 ([0003-plan-v0.1.md](0003-plan-v0.1.md)) until then. The reference checker for this text is `spec/validate/plan_v02.py`.
> **Date:** 2026-11-12
> **Spec:** VKR-L3 Plan
> **Basis:** [0003-plan-v0.1.md](0003-plan-v0.1.md), [0001-capability.md](0001-capability.md), [0012-records.md](0012-records.md), [0013-cbor-plans-ifc.md](0013-cbor-plans-ifc.md) for digests. Supersedes decision E6 for expressions: the syntax is a CEL subset, the semantics are defined here.

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in BCP 14 (RFC 2119 and RFC 8174) when they appear in capitals.

A plan is a JSON document a model may write. The Core verifies it before any step runs. The verifier's result is the security decision. The model is not.

"Verifier" is the static stage (sections 4 and 5). "Engine" is the dynamic stage (section 6). Every rule has an id. Every rejection has a stable problem code. Test vectors cite both.

## 0. What changes against v0.1

- Plans can declare typed, labelled `inputs`. A plan with inputs is a template.
- Arguments are type-checked against `input_schema` before execution. v0.1 checked member names only (R4a).
- `expr` steps are evaluated. The language is defined in section 3 and needs no CEL implementation.
- Labels carry integrity as well as confidentiality. Control flow is labelled.
- New step kinds `ask`, `declassify`, `view`. New members `when`, `on_refuse`, `retry`, `timeout_s`, `parallel`, `result`, `inputs`.
- New type `blob`. New effect `compute`. Literals may be lists and objects; `null` and fractional numbers are no longer literals.
- `field` is a dotted path, on `ref`, `item` and `over`.

Carried over unchanged: 32 steps, unique ids, `ref` to earlier steps only, `map` with `bound` 1 to 32, `approval: true` on consequential capabilities (v0.1 R7, here T-APPROVAL), and the cost rules (v0.1 R13 and R14, here E9 and T-BUDGET).

## 1. Document

The shape is [plan-v02.schema.json](../../spec/schemas/plan-v02.schema.json). No object defined in this section has members other than those listed.

### 1.1 Plan

| Member | Required | Value |
|---|---|---|
| `v` | yes | `"0.2"` |
| `goal` | no | String, at most 256 characters. Never interpreted. |
| `inputs` | no | Object: name to Input (1.2). At most 16. |
| `budget` | no | Object with any of `max` (money), `tokens` (integer), `wall_s` (integer) |
| `steps` | yes | Array of 1 to 32 steps (1.3) |
| `result` | no | A Ref (1.4) |

A plan with a non-empty `inputs` is a *template*. Binding a value to every input gives an *instance*. A plan without inputs is its own single instance.

### 1.2 Input

```json
{ "type": <schema of 2.3>, "label": { "classes": [<data class>...], "integrity": "trusted" | "untrusted" } }
```

Both members are required. An input bound by a trigger MUST be declared `untrusted`.

### 1.3 Step

A name matches `[a-z][a-z0-9_]{0,31}`. Step ids and input names share one namespace and MUST be unique in it.

Members of every step:

| Member | Kinds | Value | Default |
|---|---|---|---|
| `id` | all | Name | required |
| `kind` | all | `call`, `map`, `expr`, `ask`, `declassify`, `view` | required |
| `when` | all except `expr` | Id of an earlier `expr` step of type `bool` | none |
| `on_refuse` | all except `view` | `"stop"` or `"continue"` | `"stop"` |
| `retry` | `call`, `map` | Integer 0 to 3 | 0 |
| `timeout_s` | `call`, `map`, `ask`, `declassify` | Integer 1 to 3600 | descriptor's, else 30 |

Members by kind:

| Kind | Required | Optional |
|---|---|---|
| `call` | `capability`, `args` (object: parameter to Arg) | `approval` (boolean) |
| `map` | `capability`, `args`, `over` (Ref to a list), `bound` (integer 1 to 32) | `approval`, `parallel` (boolean) |
| `expr` | `expr` (source, section 3) | |
| `ask` | `prompt` (id in the prompt catalog) | `options` (Ref to a list), `show` (object: name to Arg) |
| `declassify` | `value` (Ref), `drop` (array of data classes, may be empty), `endorse` (boolean) | |
| `view` | `component` (id in the view catalog), `bind` (object: prop to Arg) | |

`args`, `show` and `bind` hold at most 16 entries each.

### 1.4 Arg and Ref

An Arg is exactly one of:

| Form | Meaning |
|---|---|
| `{ "lit": <literal> }` | A constant: boolean, integer, string, array of literals, or object of literals. Not `null`, not a fractional number. At most 4096 bytes as compact JSON. |
| `{ "ref": "<name>" }` | The value of that input or earlier step |
| `{ "ref": "<name>", "field": "<path>" }` | The member at `path` of that value |
| `{ "item": true }`, optionally with `"field"` | Inside the `args` of a `map` only: the current element, or a member of it |

A Ref is the `ref` form. A path is one or more member names joined by `.`. A path has no list index; indexing is done in an `expr`.

### 1.5 Limits

| Limit | Value |
|---|---|
| Plan document as compact JSON | 65536 bytes |
| Steps; inputs | 32; 16 |
| `ask` plus `declassify` steps | 4 |
| Expression source | 1024 bytes |
| Expression tokens; bracket nesting | 256; 16 |
| String produced by an expression | 4096 bytes |
| List length | 1024 |
| Value shown by `declassify` | 2048 bytes as compact JSON |

## 2. Types

### 2.1 Grammar

```
τ ::= bool | int | decimal | string
    | enum{ s1, …, sn }                 n ≥ 1, each s a string
    | list<τ>[n]                        n = maximum length, 1 ≤ n ≤ 1024
    | record{ f1: τ1, …, g1?: σ1, … }   required fields f, optional fields g
    | blob<m>                           m = a media type, or * for any
```

There is no null and no floating-point type. An optional field is present with a value or absent.

### 2.2 Values

| Type | Value |
|---|---|
| `int` | A signed 64-bit integer. Implementations MUST read JSON integers exactly. |
| `decimal` | A string matching `-?(0\|[1-9][0-9]{0,17})(\.[0-9]{1,6})?`: at most 18 integer and 6 fractional digits. An implementation holds it as an integer scaled by 10^6. |
| `string` | A Unicode string, compared and measured by code point |
| `blob<m>` | A reference `{ "digest": "sha256:<hex>", "media": <string>, "size": <integer> }`. The content is not a step value. |

**D1.** A `decimal` produced by the engine is written in canonical form: no trailing fractional zeros, no fractional point without digits after it, no negative zero. `1.50` is written `1.5`, `2.000000` is written `2`.

### 2.3 Schema form

Types are written as a subset of JSON Schema in `inputs`, `input_schema`, `output_schema` and view props.

| Type | Schema |
|---|---|
| `bool` | `{ "type": "boolean" }` |
| `int` | `{ "type": "integer" }`, optionally `minimum`, `maximum` |
| `decimal` | `{ "type": "string", "format": "decimal" }` |
| `string` | `{ "type": "string" }`, optionally `maxLength` |
| `enum` | `{ "enum": [ …strings… ] }` |
| `list<τ>[n]` | `{ "type": "array", "items": τ, "maxItems": n }` |
| `record` | `{ "type": "object", "properties": {…}, "required": […], "additionalProperties": false }` |
| `blob<m>` | `{ "type": "blob", "media": m }` |

Any other keyword, and a record without `additionalProperties: false`, makes the schema unusable (`T-SCHEMA`). `minimum`, `maximum` and `maxLength` are checked at run time only (E5, E7) and take no part in subtyping.

### 2.4 Subtyping

`σ <: τ` holds exactly when:

- **S1.** σ and τ are the same type.
- **S2.** σ is an `enum` and τ is `string`.
- **S3.** σ = `enum{A}`, τ = `enum{B}` and A ⊆ B.
- **S4.** σ = `list<σ′>[m]`, τ = `list<τ′>[n]`, σ′ <: τ′ and m ≤ n.
- **S5.** σ and τ are records; every required field of τ is a required field of σ with a subtype; every optional field of τ is absent from σ or present in σ with a subtype. σ may have further fields.
- **S6.** σ = `blob<m>` and τ is `blob<m>` or `blob<*>`.

There is no conversion between `int`, `decimal` and `string`.

**S7.** A literal is checked against the type it is used at, not typed on its own: a string literal fits `decimal` if it has the form of 2.2, and fits an `enum` if it is a member.

### 2.5 Types of step outputs

| Step | Output type |
|---|---|
| `call` | The capability's `output_schema` |
| `map` | `list<output_schema>[bound]` |
| `expr` | The type of the expression |
| `ask` with `options` of type `list<τ>[n]` | `record{ index: int, value: τ }` |
| `ask` without `options` | `string` |
| `declassify` | The type of `value` |
| `view` | None. A `view` step MUST NOT be referenced. |

## 3. Expressions

The syntax is a subset of CEL so that models and people can read it. Typing and evaluation are defined here and nowhere else. Verifier and engine MUST use one implementation.

### 3.1 Grammar

```
expr     = or [ "?" expr ":" expr ] ;
or       = and { "||" and } ;
and      = cmp { "&&" cmp } ;
cmp      = add [ ( "==" | "!=" | "<" | "<=" | ">" | ">=" | "in" ) add ] ;
add      = mul { ( "+" | "-" ) mul } ;
mul      = unary { ( "*" | "/" | "%" ) unary } ;
unary    = { "!" | "-" } postfix ;
postfix  = primary { "." ident [ "(" args ")" ] | "[" expr "]" } ;
primary  = "true" | "false" | int | string | ident [ "(" args ")" ]
         | "(" expr ")" | "[" args "]" ;
args     = [ expr { "," expr } ] ;
int      = digit { digit } ;
string   = '"' { char | "\" ( '"' | "\" | "n" | "t" | "u" hex hex hex hex ) } '"' ;
ident    = ( letter | "_" ) { letter | digit | "_" } ;
```

- **G1.** Whitespace is space, tab and line feed, between tokens only. `letter` is `a` to `z` and `A` to `Z`; `digit` is `0` to `9`. A string literal does not contain a raw line feed.
- **G2.** An integer literal above 2^63 − 1 is a syntax error.
- **G3.** A comparison does not chain: `a < b < c` is a syntax error.
- **G4.** *Nesting* is the number of enclosing `( … )`, `[ … ]`, argument lists and ternary branches at a point in the source. Nesting above 16 is a syntax error. A parser MUST check it without recursing deeper than the limit. Operator chains of one precedence level are not nesting.
- **G5.** More than 256 tokens, or more than 1024 bytes of source, is a syntax error.

Every syntax error is problem `W-PARSE`.

### 3.2 Names

A bare identifier not followed by `(` MUST be the name of an input or of an earlier step. There are no other variables.

### 3.3 Typing

| Form | Operand types | Result |
|---|---|---|
| `true`, `false`; integer literal; string literal | | `bool`; `int`; `string` |
| `[e1, …, en]`, n ≥ 1 | all the same scalar type τ | `list<τ>[n]` |
| `!e` | `bool` | `bool` |
| `-e` | `int` or `decimal` | the same |
| `a && b`, `a \|\| b` | `bool`, `bool` | `bool` |
| `c ? a : b` | `bool`, σ, τ with σ <: τ or τ <: σ | the supertype |
| `a + b`, `a - b` | both `int`, or both `decimal` | the same |
| `a + b` | both `string` or `enum` | `string` |
| `a * b`, `a / b`, `a % b` | both `int` | `int` |
| `a == b`, `a != b` | the same scalar type; `enum` and `string` mix | `bool` |
| `a < b`, `<=`, `>`, `>=` | both `int`, both `decimal`, or both `string` or `enum` | `bool` |
| `a in l` | scalar τ and `list<τ>[n]`; `enum` and `string` mix | `bool` |
| `e.f` | record with required field `f: τ` | τ |
| `e.f` (**X-OPT**) | record with optional field `f?: τ` | τ; undefined when absent |
| `e.size`, `e.media` | `blob` | `int`, `string` |
| `l[i]` | `list<τ>[n]`, `int` | τ; undefined outside the list |

Scalar types are `bool`, `int`, `decimal`, `string` and `enum`. Lists, records and blobs cannot be compared. An empty list literal is a type error. Every type error is problem `T-EXPR`.

### 3.4 Functions

| Function | Signature | Meaning |
|---|---|---|
| `size(x)` | `string`, `enum` or list to `int` | Code points, or elements |
| `has(e.f)` | a selection ending in an optional field, to `bool` | Whether the field is present. Does not evaluate `e.f`. |
| `done(s)` | the name of a step to `bool` | Whether step `s` ended `completed` |
| `sum(l)` | `list<int>` to `int`; `list<decimal>` to `decimal` | The sum; zero for an empty list |
| `dec(s)` | a string literal in the form of 2.2, to `decimal` | That decimal |
| `s.startsWith(p)`, `s.endsWith(p)`, `s.contains(p)` | strings to `bool` | By code point |

There are no other functions, no macros and no user-defined functions. `done` does not accept an input name.

### 3.5 Evaluation

An expression evaluates to a value or to *undefined*. It raises no error and always terminates.

- **V1.** Undefined arises only from: an `int` result outside 64 bits; `/` or `%` by zero; a quotient outside 64 bits (`/` and `%` of the least integer by −1); a `decimal` result with more than 18 integer digits; an index outside `0 ≤ i < size`; selecting an absent optional field; a string result above 4096 bytes; a name whose step did not end `completed`.
- **V2.** An operator or function with an undefined operand is undefined, except as V3 to V5 say.
- **V3.** `a && b`: if `a` is `false` the result is `false` and `b` is not evaluated; if `a` is undefined the result is undefined. `a || b` likewise with `true`.
- **V4.** `c ? a : b` evaluates `c`, then only the selected branch.
- **V5.** `has(e.f)` is undefined only if `e` is. `done(s)` is never undefined.
- **V6.** `/` truncates towards zero. `%` has the sign of the dividend.
- **V7.** `decimal` addition, subtraction and negation are exact. Comparison is numeric: `dec("1.50") == dec("1.5")`.
- **V8.** Operands are evaluated left to right. Evaluation has no side effects.

Termination: there is no binding construct and no recursion, and `sum` is linear in a list of at most 1024 elements.

### 3.6 Result of an `expr` step

With a value, the step ends `completed` with that value (D1 applies). When undefined, it ends `skipped` with reason `undefined` and E4 applies. An `expr` step never ends `failed`.

## 4. Static checks

The verifier takes a plan, a capability catalog, a prompt catalog, a view catalog and a policy. It accepts, or rejects with a non-empty list of problems. A problem is a code, the id of the step it concerns if any, and the parameter or prop if any.

- **C1.** The checks run in three stages: 4.1, 4.2, 4.3. A stage runs only if the earlier ones found nothing.
- **C2.** Within a stage a verifier MUST report every problem it finds, sorted by step order, then code, then parameter name. Problems without a step come last, except `W-JSON` and `W-VERSION`, which come first.

### 4.1 Well-formedness

| Code | Rule |
|---|---|
| `W-JSON` | The document is a JSON object within the limits of 1.5; the plan, `budget` and every input have only the members this document defines, with values of the right shape. |
| `W-VERSION` | `v` is `"0.2"`. |
| `W-ID` | Every name matches the pattern; step ids and input names are unique in one namespace. |
| `W-KIND` | `kind` is one of the six. |
| `W-FIELD` | A step has exactly the required members of its kind and only its optional ones (1.3), each with a value in range; every Arg has one of the forms of 1.4. |
| `W-REF` | Every `ref`, `when`, and every name in an expression denotes an input or an earlier step. A `view` step is never referenced. |
| `W-ITEM` | `item` occurs only in the `args` of a `map`. |
| `W-CAP` | The capability of every `call` and `map` is in the catalog. |
| `W-PROMPT` | `prompt` is in the prompt catalog; `component` is in the view catalog. |
| `W-PARSE` | Every expression parses (3.1). |
| `W-COUNT` | At most four steps are `ask` or `declassify`. |

### 4.2 Typing

| Code | Rule |
|---|---|
| `T-SCHEMA` | `input_schema` and `output_schema` of every capability used, and every input type, are in the subset of 2.3; `input_schema` is a record. |
| `T-EXPR` | Every expression is well typed (3.3, 3.4). |
| `T-WHEN` | `when` names an `expr` step of type `bool`. |
| `T-PATH` | Every `field` path exists in the type it is followed through and passes through no optional field. |
| `T-ARGS` | The args of a `call` or `map`: no parameter outside `input_schema`; every required parameter present; a Ref or `item` argument is a subtype of the parameter type; a literal fits it (S7). |
| `T-OVER` | `over` has a list type. `item` has the element type. |
| `T-APPROVAL` | A step on a capability with `consequential: true` has `approval: true`. One approval on a `map` covers every repetition up to `bound`. |
| `T-PAR` | `parallel: true` only on a capability whose effects are within `compute` and `read`. |
| `T-RETRY` | `retry` above 0 only on a capability whose effects are within `compute` and `read`, or with `idempotent: true`. |
| `T-ASK` | `options`, if present, has a list type. Every `show` value has a scalar type. |
| `T-DECL` | `value` has a scalar type, or a record type whose fields are all scalar. |
| `T-VIEW` | Every bound prop exists; every required prop is bound; each value is a subtype of the prop type, or a literal that fits it. |
| `T-RESULT` | `result` resolves to a type. |
| `T-BUDGET` | The worst-case cost (E9) is within `budget` in every dimension the plan declares. A plan with a `metered` step MUST declare `budget.max` in that currency. Amounts in two currencies are a problem. |

### 4.3 Flow

The verifier computes labels (5.2, 5.3), generates flows (5.4), applies the fixed rules (5.5), then the policy (5.6). Codes: `H1` to `H5`, `Q1`, `F-POLICY`.

## 5. Labels and flows

### 5.1 Lattice

A label is a pair (C, I). C is a finite set of data classes. I is `trusted` or `untrusted`, with `trusted` < `untrusted`.

- **K1.** Class `a` *covers* class `b` when `b` is `a` or begins with `a` followed by `.`. `finance` covers `finance` and `finance.transactions`.
- **K2.** A class set is kept in normal form: no member is covered by another member. `{finance, finance.transactions}` is `{finance}`.
- **K3.** (C1, I1) ⊑ (C2, I2) iff every class of C1 is covered by a class of C2, and I1 ≤ I2.
- **K4.** (C1, I1) ⊔ (C2, I2) = (normal form of C1 ∪ C2, max(I1, I2)).
- **K5.** ⊥ = (∅, `trusted`).
- **K6.** A class is *secret* when `secrets` covers it.

Labels are per step, not per field, with the one exception of L-ASK.

### 5.2 Value labels

L(x) is the label of the output of step x, or of input x. pc(s) is defined in 5.3. For a capability c, D(c) = (`data_classes`, `integrity`) from its descriptor; a missing `integrity` is `untrusted`.

| Rule | Subject | Label |
|---|---|---|
| **L-LIT** | a literal | ⊥ |
| **L-INPUT** | input x | As declared |
| **L-REF** | a Ref to x, with or without `field` | L(x); for an `ask` with `options`, see L-ASK |
| **L-ITEM** | `item` in a `map` over r | L(r) |
| **L-CALL** | `call` on c with args a1…an | D(c) ⊔ L(a1) ⊔ … ⊔ L(an) ⊔ pc(s) |
| **L-MAP** | `map` on c over r | D(c) ⊔ L(r) ⊔ L(a1) ⊔ … ⊔ L(an) ⊔ pc(s) |
| **L-EXPR** | `expr` e | pc(s) ⊔ the join of L(x) for every name x in e, including inside `done()` and `has()` |
| **L-ASK** | `ask` | The *choice* label is (C, `trusted`), C being the classes of pc(s), of `options` and of every `show` value. Without `options`, L(s) is the choice label. With `options`, a Ref or expression selecting `.index` has the choice label, one selecting `.value` has L(options), and L(s) is their join. |
| **L-DECL** | `declassify` of v | Let (C, I) = L(v) ⊔ pc(s). The label is (C without every class covered by a member of `drop`, I′), where I′ is `trusted` if `endorse` is true and I otherwise. |
| **L-VIEW** | `view` | ⊥. It has no output. |

L-EXPR makes `done(x)` carry L(x). L(x) already holds x's arguments, its capability's label and pc(x), so whether x completed is as sensitive and as untrusted as x.

### 5.3 Control labels

deps(s) is every input or step that s names in a `ref`, in `over`, `options`, `value` or `when`, or by name in its expression, except names that occur only inside `done()`.

- **P1.** pc(s) starts as ⊥.
- **P2.** If s has `when: w`, then pc(s) ⊔= L(w).
- **P3.** For each d in deps(s): pc(s) ⊔= O(d), where O(d) is L(d) if d is a step with `on_refuse: "continue"`, and pc(d) otherwise.
- **P4.** For an input x, pc(x) = ⊥.

Reading of P3: s runs only if its dependencies completed (E3). If d stops the plan when it does not complete, then s being reached says nothing beyond pc(d). If d lets the plan go on, then whether s runs reveals d's outcome, which is as sensitive as d's output.

- **N1 (accepted residual).** With `on_refuse: "stop"`, a later step running reveals that every earlier step completed. This termination channel carries at most one bit per run and can only suppress effects, never cause one.

### 5.4 Flows

A flow is a value label, a control label, and a sink. The verifier generates, in this order:

- **F1.** For each `call` or `map` step s on capability c, for each effect of c other than `compute` in registry order, for each arg p in name order: (L(arg p), pc′(s), capability sink: c, the effect, p, the `role` of p, the `quarantine` of c).
- **F2.** As F1 for a step with no args: one flow per effect with value label ⊥, an empty parameter name and role `payload`.
- **F3.** For each `view` step and each bound prop in name order: (L(arg), pc(s), view sink: the prop and its `kind`).
- **F4.** For each `ask` step: for each `show` value and for `options`, in name order with `options` under the name `options`: (L(arg), pc(s), ask sink). An `ask` with neither yields one flow (⊥, pc(s), ask sink) with an empty name.
- **F5.** For `result`: (L(result), ⊥, result sink).

pc′(s) is pc(s) with integrity `trusted` if A1 applies to s, and pc(s) otherwise. A capability whose only effect is `compute` is not a sink and yields no flow.

### 5.5 Fixed rules

Let A = value label ⊔ control label of a flow. No policy can permit what a fixed rule denies.

| Code | Denied when |
|---|---|
| `H1` | A has a secret class, and the sink is a capability with effect `egress`, a view, an ask, or the result |
| `H2` | The value label is `untrusted`, the sink is a capability parameter with role `target`, and the effect is not `read` |
| `H3` | The control label is `untrusted`, and the effect is `delete`, `execute` or `egress`, or it is `write` on a capability without `quarantine` |
| `H4` | A `declassify` step whose `value` has a secret class, or whose `drop` list contains a secret class |
| `H5` | The value label is `untrusted` and the sink is a view prop whose `kind` is not `text` |
| `Q1` | A descriptor in the catalog has `quarantine: true` and effects other than exactly `["write"]` |

`H1` to `H3` and `H5` are reported with the step and the parameter of the flow; `H4` with the step; `Q1` with the capability id as parameter.

### 5.6 Policy

Every flow that no fixed rule denies goes to the owner's policy, which permits or denies it (`F-POLICY`). A `declassify` with a non-empty `drop` additionally needs the policy to permit the action `declassify` on each dropped class (`F-POLICY` on the step).

- **O1.** A verifier run without a policy MUST deny every flow whose A is not ⊥, and every `declassify` with a non-empty `drop`.
- **O2.** How a policy is written and evaluated is VKR-L2 and spec 0013 §4. The vectors use two policies only: `permit-all` and `none` (O1).

### 5.7 Endorsement

`untrusted` becomes `trusted` in exactly three ways.

- **A1, approval with provenance.** If s is a `call` or `map` with `approval: true` and pc(s) is `untrusted`, the verifier marks s `provenance`. The engine MUST then show, in the approval, every `when` condition on the path to s with its value and the steps it was computed from, and MUST bind the approval to a digest that covers them. For such a step, flows use pc′. A1 changes the control label only: H2 still applies to the values.
- **A2, `declassify` with `endorse`.** The Trusted UI shows the exact value and the steps it was computed from. The approval binds to the digest of the value. A value above 2048 bytes as compact JSON ends the step `refused` with `too-large`.
- **A3, `ask`.** The owner's choice is `trusted`. What was chosen keeps its label. If pc(s) is `untrusted`, the engine MUST show the conditions as in A1.

### 5.8 Quarantine

A capability with `quarantine: true` stores what it is given. The stored record takes effect only through a later, separate step.

- **Q2.** The store MUST persist, with each record, the label A of the flows that produced it.
- **Q3.** A capability that returns stored records MUST return their persisted labels as the run-time label of its output (E8).
- **Q4.** The store MUST enforce a quota of quarantined records per mandate and refuse beyond it with `quota-exceeded`.
- **Q5.** The capability that gives quarantined records effect is an ordinary capability without `quarantine`. Its inputs read from the store are `untrusted`, so H2 applies to them, and H3 applies unless A1 does.

Q3 with E8 is what stops a second plan from reading a draft back as trusted local data: a reader whose descriptor does not declare `untrusted` is refused at run time.

## 6. Execution

The engine runs an instance only if the verifier accepted its template against the same catalog digest and the same policy digest.

### 6.1 Step states

Every step ends in exactly one state.

| State | Meaning | Reasons |
|---|---|---|
| `completed` | Ran and produced its output | |
| `skipped` | Did not run | `when`, `dependency`, `stopped`, `undefined` |
| `refused` | Rejected before any effect | `bad-input`, `bound-exceeded`, `label-exceeds-static`, `quota-exceeded`, `too-large` |
| `denied` | No grant, no approval, or the owner declined | `unauthorized`, `policy-denied`, `approval-denied`, `approval-timeout`, `budget-exceeded` |
| `failed` | The backend reported an error, or the timeout passed | `bad-output`, `unavailable`, or a backend code |

Reason codes other than the four skip reasons are in [registries/refusal-reasons.md](../../spec/registries/refusal-reasons.md).

### 6.2 Rules

- **E1.** Steps are settled in list order.
- **E2.** If s has `when: w`, w completed and its value is `false`, s is `skipped` (`when`).
- **E3.** If any step in deps(s) is not `completed`, s is `skipped` (`dependency`). Names that occur only inside `done()` are not in deps(s).
- **E4.** If s ends in any state other than `completed`, for a reason other than `when`, `dependency` or `stopped`, then `on_refuse` decides. With `stop`, every later step is `skipped` (`stopped`). With `continue`, execution goes on.
- **E5.** Before dispatch the engine resolves the args and checks them against `input_schema`, including `minimum`, `maximum` and `maxLength`. A violation is `refused` (`bad-input`).
- **E6.** For `map`: if the list is longer than `bound`, the step is `refused` (`bound-exceeded`) and no element runs. Otherwise the capability runs once per element and the output list has the order of the input list. If an element does not complete, the step takes that element's state and reason, later elements do not run, and the step has no output.
- **E7.** After dispatch the engine checks the output against `output_schema`. A violation is `failed` (`bad-output`).
- **E8.** If a backend reports a run-time label for an output (Q3), the engine compares it with the static label L(s). If it is not ⊑ L(s), the step is `refused` (`label-exceeds-static`) and the output is discarded.
- **E9.** Worst-case cost: the sum over all `call` and `map` steps, as if every step ran, every `map` ran `bound` times, and every attempt of `retry` was used. Money: a `free` capability costs zero, a `metered` one its `cost.max`. Tokens: `model.max_tokens`. Seconds: the step's `timeout_s`. `when` does not reduce it.
- **E10.** `retry` applies to the state `failed` only, up to `retry` further attempts. Each attempt of an airlock step is authorised on its own: it has its own decision entry carrying the attempt number, and its own effect permit bound to that entry. A permit is consumed by the first attempt and MUST NOT be reused.

### 6.3 Lanes

The lane of a step follows from its kind and its descriptor's effects. A plan cannot choose it.

| Lane | Steps | Permit | Audit |
|---|---|---|---|
| Internal | `expr`, `view`; `call` and `map` whose only effect is `compute` | None | One `note` entry, may be buffered |
| Read | Effects within `compute` and `read`, including `read` | Required | One `note` entry, may be buffered; durable at once if L(s) has a secret class |
| Airlock | Any of `write`, `delete`, `execute`, `egress`; `ask`; `declassify` | Required for capabilities | A `decision` entry, durable before the effect; then an `outcome` entry |

- **E11.** Entries are appended to one chain in the order produced. Making the chain durable up to and including an entry is a *sync*. A sync MUST follow every airlock `decision` before its effect begins, and the last entry of a run. All buffered entries thus become durable no later than the next airlock decision.
- **E12.** Airlock steps run one at a time, in list order.
- **E13.** Internal and read steps MAY run concurrently when none depends on another, and a `map` with `parallel: true` MAY run its elements concurrently. Concurrency MUST NOT change any output, any state, or the chain: entries are ordered by step, then element index, then attempt.
- **E14.** A step that is `skipped` has one `note` entry. A step that is `refused` or `denied` before dispatch has one entry and no `outcome`: a `decision` followed by a sync in the airlock lane, a `note` otherwise.

### 6.4 Result

The run result is the value of `result` if the step it names completed, else nothing. A run reports the state and reason of every step.

## 7. Descriptor additions (VKR-L1 v0.2)

The shape is [capability-descriptor.schema.json](../../spec/schemas/capability-descriptor.schema.json). A descriptor that uses any member or value of this section has `v: "0.2"`. A capability can be used from a v0.2 plan only if `input_schema` and `output_schema` are in the subset of 2.3.

| Member | Value | Default | Used by |
|---|---|---|---|
| `integrity` | `"trusted"` or `"untrusted"` | `"untrusted"` | L-CALL |
| `roles` | Object: parameter to `"payload"` or `"target"` | Every parameter `"payload"` | H2 |
| `quarantine` | Boolean | `false` | H3, Q1 to Q5 |
| `idempotent` | Boolean | `false` | T-RETRY |
| `timeout_s` | Integer 1 to 3600 | 30 | E9 |
| `model` | Object (7.1) | None | 7.1 |

New effect code **`compute`**: the capability computes its output from its arguments only. It observes and changes nothing outside the call. `compute` is not consequential and needs no data class.

- **R-ROLE.** A parameter that names a recipient, a destination, a path, a URL, an account or a command MUST have role `target`. Declaring such a parameter `payload` is a descriptor defect, to be caught in catalog review.
- **R-INT.** `integrity: "trusted"` is a claim that nothing outside the owner's control can influence the output beyond what the arguments carry. Mail, calendar entries from others, web pages and files of foreign origin are `untrusted`.

### 7.1 Inference capabilities

A capability with a `model` member runs a local model.

| Member of `model` | Value |
|---|---|
| `base` | `sha256:` digest of the base model file |
| `adapter` | `sha256:` digest of the signed adapter package; absent for the base model alone |
| `max_tokens` | Integer 1 to 4096 |

- **M1.** `effects` MUST be exactly `["compute"]`.
- **M2.** `integrity` MUST be absent or `"untrusted"`.
- **M3.** `output_schema` MUST be a record with a required field `confidence` of type `int`. Decoding is constrained to `output_schema` without `confidence`. The host adds the field; the model cannot write it.
- **M4.** Decoding is greedy. There is no sampling temperature and no seed.
- **M5.** `base` and `adapter` are members of the descriptor and therefore covered by the catalog digest. A changed adapter is a changed catalog, and templates released against the old one need a new release.

### 7.2 Confidence

`confidence` is an integer from 0 to 1000, computed by the host.

- **N-C1.** A *free* token is an output token at whose position the constraint allowed more than one token.
- **N-C2.** Let p1…pk be the probabilities the model gave the chosen free tokens, each renormalised over the tokens the constraint allowed at its position.
- **N-C3.** `confidence` = floor(1000 × (p1 × … × pk)^(1/k)). With k = 0, `confidence` is 1000.

The value is not reproducible across hardware or builds. Verification MUST NOT depend on it, and vectors supply it as scripted output. Calibration, and the threshold a template uses, are set per adapter bundle from measurement. Deterministic validators SHOULD gate before `confidence` does.

### 7.3 Catalogs for prompts and views

- A prompt catalog maps a prompt id to a fixed template. A model cannot supply the text of a question. Values bound through `show` and `options` are rendered as data, never as markup, and `untrusted` values are visibly marked.
- A view catalog maps a component id to its props. Each prop has a `schema` (2.3), a `kind` (`text`, `url`, `action` or `markup`) and optionally `required`. An action in a view never calls a capability; it may answer an open `ask` or submit a new intent, which goes through planner and verifier again.
- A view catalog MAY be carried as an A2UI catalog. Then it MUST declare `protocolVersion` `1.0`, and its digest is part of the catalog digest (section 8); a catalog of another protocol version is a different catalog. The host MUST refuse agent-side function calls: every function stays at the default `allowedCallers: rendererOnly`, and a catalog that declares `callAgentFunction` targets is rejected. Bound values reach the renderer only through the data model, never through component definitions or catalog `instructions`. A `userMessage` action yields a new intent with integrity `untrusted`. The prop `kind` of this section travels as a catalog extension; a renderer that does not know the extension MUST NOT render the view.

## 8. Digests

Digests follow spec 0013: SHA-256, unpadded base64url, over the `dcbor` bytes (spec 0012 §2).

| Digest | Over |
|---|---|
| Template digest | The plan document |
| Catalog digest | The array of the descriptors the plan references, sorted by `id` (0013), including the members of section 7 |
| Input digest | The object mapping each input name to its bound value; the empty object for a plan without inputs |
| Instance digest | `{ "template": <digest>, "catalog": <digest>, "inputs": <digest> }` |

An owner's release of a template is a signed statement over the template digest, the catalog digest and the policy digest. Grants, approvals and effect permits bind to the instance digest.

## 9. Conformance

Vectors live in `spec/test-vectors/plan-v0.2/`, one file per operation, in the envelope of [vector.schema.json](../../spec/test-vectors/vector.schema.json). Every `expected` is a `value` and MUST be produced exactly. `spec.section` cites rule ids of this document.

| Operation | Input | Value |
|---|---|---|
| `expr-eval` | `env` (name to `{type, value}`, or `{type, step: true, completed: false}` for a step that did not complete), `expr` | `{type, value}`, `{type, undefined: true}`, or `{error}` with `W-PARSE`, `W-REF` or `T-EXPR`. `type` is written in the grammar of 2.1, record fields and enum members sorted. |
| `plan-verify` | `plan`, `catalog` (array of descriptors), `policy` (`permit-all` or `none`), optional `prompts`, `views` | `{verdict: "accept"}` or `{verdict: "reject", problems}` in the order of C2 |
| `plan-flows` | `plan`, `catalog`, optional `prompts`, `views` | `{labels, flows}`: per step `value` and `pc` (and for an `ask` with options `index` and `chosen`; `provenance: true` under A1), and the flow list in the order of 5.4, before any rule or policy |
| `plan-run` | An accepted `plan`, `catalog`, optional `inputs`, `script` (step id to scripted outcome), optional `prompts`, `views` | `{steps, trace, result?}`: state, reason and output of every step, and the audit chain as entries `{step, entry, element?, attempt?}` with `{sync: true}` markers (E11) |

A label is written `{ "classes": [sorted], "integrity": … }`. Scripted outcomes for `plan-run`: a `call` gives `{output}` or `{state, reason}`, optionally `label` (E8), `approval: "declined"`, or `attempts` (a list of outcomes, E10); a `map` gives `{elements: [outcome…]}`; an `ask` gives `{answer: {index}}`, `{answer: <string>}` or `{state, reason}`; a `declassify` gives `{approve: <boolean>}`. Grants are assumed to cover every step.

The expectations in the first version of the suite were computed by the reference checker and compared with an intent stated per vector in `spec/test-vectors/tools/gen_plan_v02_vectors.py`. They have not yet been confirmed by a second implementation.

## 10. Out of scope

- Loops, recursion and comprehension macros. The bounded `map` is the only repetition.
- Per-field labels. A capability that returns a public id next to a confidential body taints both.
- Replanning: nothing lets a run feed results back to a planner. Planned for v0.3.
- Triggers, grants, the audit record format, WASI worlds and the Trusted UI surface, except for what sections 5.7, 5.8 and 6.3 require of them.
- A text syntax for people. The interchange form is JSON; `dcbor` is the canonical encoding for digests and signatures.
